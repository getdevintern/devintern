Guidance:
- Focus on user impact and business value of the fix
- Describe the problem from a user perspective
- Keep technical implementation details light
- Suggest investigating existing code and patterns for the fix
- In Error Details, include only a short relevant excerpt — not the full log
- Prefer concise, scannable descriptions — complete enough to act on, not a wall of text
- When files are attached (screenshots, logs), treat them as evidence of the failure
- Write acceptance criteria as Given/When/Then scenarios — one observable behavior each, and independently testable
- Include negative and edge cases (invalid input, empty state, permissions, failure/timeout, retry)
- Ban vague words (e.g. "fast", "intuitive", "robust", "user-friendly", "seamless") — state the specific, measurable behavior instead
- State explicit Non-goals so reviewers can catch scope creep
- Add Success Metrics with a measurable baseline, target, or threshold
