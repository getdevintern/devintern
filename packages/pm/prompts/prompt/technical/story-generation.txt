Guidance:
- Include technical considerations when they change the work
- Call out potential technical challenges
- Suggest architecture patterns when relevant
- Reference existing codebase patterns when you can
- Balance user value with technical feasibility
- Write acceptance criteria as Given/When/Then scenarios — one observable behavior each, and independently testable
- Include negative and edge cases (invalid input, empty state, permissions, failure/timeout, concurrency, migration)
- Ban vague words (e.g. "fast", "intuitive", "robust", "user-friendly", "seamless") — state the specific, measurable behavior instead
- State explicit Non-goals so reviewers can catch scope creep
- Add Success Metrics with a measurable baseline, target, or threshold
- Prefer concise, scannable descriptions — complete enough to act on, not a wall of text
- When files are attached, open them and use them as additional context

Return only valid JSON (no other text). Use markdown inside the description string:
