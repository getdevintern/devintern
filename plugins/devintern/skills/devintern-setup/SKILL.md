# Set up DevIntern

Recommend workspace/worker mode as the standard DevIntern Code setup, including for a single repository. It provides ongoing task acquisition, PR follow-up, schedules, and centralized configuration. For a general request to set up DevIntern, guide the user toward a workspace worker with relay-backed integrations. Honor explicit requests for a one-off interactive CLI run; those do not require a resident service or worker entitlement. Do not treat a successful standalone task as completion of requested worker setup.

Use the [quick start](https://devintern.com/docs/code/quick-start), [configuration guide](https://devintern.com/docs/code/configuration), and [worker guide](https://devintern.com/docs/code/worker). In a source checkout, read the corresponding `docs/code/*.md` files and implementation when needed. Installed skills must not assume a source checkout or other DevIntern skills are present. Check installed command help before using flags from newer documentation.

## Establish the destination and existing state

Identify the execution host, repository remotes, chosen agent, task source, and desired PR/review behavior. Reuse working configuration and authentication. Inspect credential names and presence without printing values; do not dump `.env`, session, or relay files into tool output. Preserve existing settings, repository/team identifiers, and file permissions.

The default worker config is `~/.devintern/workspace.toml`. Honor `DEVINTERN_WORKSPACE_DIR` and explicit `--workspace /path/to/workspace.toml` selections on commands that support them. Secrets, git credentials, and agent authentication must work on the worker host, even when authorization happens in a browser on another machine.

Read [Integrations](references/integrations.md) when configuring source control, tracker credentials, provider authorization, or relay connections. Code-host access, task-tracker access, DevIntern sign-in, and agent authentication are separate checks.

Actively help complete provider setup through available browser automation, such as browser-use, Chrome DevTools Protocol (CDP), or another browser tool. This can include GitHub App authorization, repository selection, and tracker webhook settings. Use an existing authorized browser connection when available; no particular browser tool is required. Let the user complete login, MFA, or admin approval when needed, then resume setup and verify the CLI result.

For a new worker with supported code-host/tracker integrations, recommend the hosted relay as the standard setup. Provider webhooks reach DevIntern's relay and the worker connects outbound, so the worker needs no public webhook endpoint, inbound port, tunnel, or customer-owned GitHub App. Include relay pairing in the normal integration setup and retain polling as fallback. Honor an explicit polling-only, no-relay, or air-gapped choice and preserve existing delivery choices when making unrelated changes. Standalone CLI tasks and local-only automations do not need relay pairing.

## Prepare the runtime and configuration

- Check Bun, Git, `devintern`, and the selected agent CLI on the execution host. If installation is requested and DevIntern is absent, use `bun install -g @getdevintern/code`. Follow the runtime or selected agent's official instructions when those prerequisites are absent; preserve the user's agent choice. Configure `AGENT_HARNESS` in the environment used by the worker. Finding the executable alone does not prove the agent is authenticated.
- For a guided setup in the user's own terminal, `devintern worker init` inside the checkout reuses project credentials or offers tracker setup, configures the workspace, validates the task query, offers relay pairing, and optionally installs/starts a user service. A separate `devintern init` run is not a prerequisite. Its prompts are for a person at a terminal: never pipe guessed answers into it or drive it through a pseudo-terminal. `worker init --no-service` skips the service offer. Use project `devintern init` for an explicitly requested standalone CLI setup.
- For agent-driven worker setup, use `devintern worker init --non-interactive` inside the checkout instead of `worker scaffold` plus hand-editing `workspace.toml` and `.env`. Example: `devintern worker init --non-interactive --tracker jira --task-query '<query>' --repo-from-cwd --json`. Supply tracker credentials and `GITHUB_TOKEN` through the environment or `--env-file <path>` (the file must be mode `0600`; it is saved to the workspace `.env`). Secrets are never flags. On an existing workspace it refuses to change anything without `--yes`; with `--yes` it updates only the tracker, `task_query`, and repository named by the flags, so confirm with the user before passing it. With `--json`, stdout is one document (`schema` `devintern.worker-init`, `version` 1): read `result`, `error` (input problems, which name every missing flag and variable), each `checks[]` entry's `name`/`status` (`pass`/`warn`/`action`/`fail`/`skipped`)/`message`/`hint`, `filesWritten`, `nextSteps[].command`, and `signIn`. `nextSteps[].id` can be `install-agent` (install the configured agent CLI; `start` and `service` are then withheld). `result` is `success` (exit 0), `action_required` (exit 2: configuration saved and nothing broken, but nobody is signed in yet, so the 14-day free Worker Pilot, no card required, has not started), or `failure` (exit 1); treat an unknown value as not ready. Do not report `action_required` as a broken setup. The checks match `worker doctor` plus a live credential probe. It never pairs the relay, installs a service, or starts the worker; relay those `nextSteps` (such as `devintern worker connect`) to the user, and install the background service with `devintern worker service install` (see [Verify and activate](#verify-and-activate)) when activation is requested. Sign-in follows the next bullet.
- Sign-in without a terminal: add `--sign-in <method>` (`github`, `google`, `x`, or the user's email address; ask which they use on devintern.com) to the init command. When sign-in is needed, the JSON then has `signIn` (`url`, `method`, `expiresAt`, `complete`). Show the user `url` (for email there is no URL: the link arrives in their inbox) and say that after signing in the browser lands on a `127.0.0.1` page that does not load, which is expected. Then either the user runs the `complete` command on the worker host with that page's full address in single quotes, or the user pastes that address to you and you run the `complete` command on the worker host. Pasting this address is the one allowed exception to never handling secrets in chat: it holds a single-use code that expires within minutes and is useless without the verifier stored owner-only on the worker host. Use it at once, only in that command, and never ask for or paste anything else (tokens, session files, `.env` values). A failed `complete` (expired, already used, wrong host) means start over with `devintern worker login <method> --no-wait --json`. Without `--sign-in`, run that same command yourself for the same flow. On an older CLI whose `devintern worker login --help` lacks `--no-wait`, have the user run `devintern worker login <method>` in a terminal on the worker host. If `devintern worker init --help` does not list `--non-interactive`, the installed CLI predates it: fall back to `devintern worker scaffold` and `devintern worker add-repo`, set `[defaults].tracker` and `task_query`, put credentials in the workspace `.env`, and verify with `worker doctor`.
- Relay pairing and Sentry without a terminal: add `--json` to `devintern worker connect <target>` for one document on stdout (`schema` `devintern.worker-connect`, `version` 1; text goes to stderr). `result` is `connected` or `pending` (exit 0), `action_required` (exit 2, nobody is signed in: run the `nextSteps` `sign-in` command, `devintern worker login <method> --no-wait --json`, then retry), or `failure` (exit 1, `error` and `code`). For GitHub, `devintern worker connect github --no-wait --json` prints `pairing.installUrl` and exits; show it to the user, who opens it in any browser and approves the DevIntern GitHub App. Then run `devintern worker connect github --status --json` on the worker host: `pending` means not approved yet (wait for the user, do not loop quickly), `connected` means registered, `failure` with `code` `pairing_expired` means start over with `--no-wait`. With several GitHub accounts repeat the pair until nothing is left. For Sentry, `devintern worker connect sentry --org <slug> --project <slug> [--repo <name>] [--sentry-url <url>] --json` needs the auth token in `SENTRY_AUTH_TOKEN` or in a `0600` `--env-file <path>`; never a flag, never in chat. An existing monitor is only changed with `--yes`, so confirm with the user first. If `devintern worker connect --help` lacks `--json`, the installed CLI predates these flags: have the user run the command in a terminal.
- Store shared worker credentials in workspace `.env`, repo credentials in repo environment layers, and tracker credentials in the relevant team layers. Prefer owner-only secret files, preserve `0600`, and keep secrets out of version control and summaries. A checkout's project `.env` is not automatically loaded by workspace execution. See [workspace configuration](https://devintern.com/docs/code/workspaces) for exact precedence and routing.
- For unattended work, check an active Worker Pilot or automation license. The Pilot is per DevIntern account, so a host always needs a sign-in for it; its 14 days start when the worker first starts. Use `devintern worker login <method> [--workspace /path/to/workspace.toml]` when worker sign-in is needed and supported; project `devintern login` alone is not proof that the selected worker is signed in. Paid license use does not by itself require sign-in; hosted relay pairing does. Never activate a paid subscription merely to complete setup.

Configure only the requested sources and policies. A single repo needs no routing rules. Multiple tracker sources use `[[teams]]`; a team fixed to one codebase can set `repo`, otherwise use unambiguous routing rules. Select a narrow, user-intended ready-work query in the tracker's query language. Do not execute `devintern --query` as a read-only connection test: it can process matching tasks. Automations can run without tracker credentials or a polling query; the current schema still requires `[defaults].tracker`.

For detailed workspace changes, use `devintern-workspace` when available, or consult the workspace guide directly. Recurring prompts, estimation sweeps, Sentry monitor policies, pipelines, quiet hours, and concurrency do not need to be enabled for basic setup. One-off dispatch uses `devintern-delegate` when available.

## Verify and activate

Use read-only provider checks for the intended repository, tracker project, query, and configured workflow states. Run `devintern worker doctor --json` (with `--workspace /path/to/workspace.toml` for a nondefault workspace) as the readiness gate before starting a worker and after config edits. It changes nothing and is safe while a worker runs. Stdout is one document (`schema` `devintern.worker-doctor`, `version` 1) with the same `checks[]` shape as `worker init --json` (`name`, `label`, `status`, `message`, `hint`), `result`, and `nextSteps[]` (`id`, `message`, `command`). Treat `result` `failure` (exit 1) as a blocker, report `warn` checks to the user instead of claiming readiness, and treat an unknown `result` as not ready. `action_required` (exit 2) means the only step left is signing in to start the Worker Pilot: run the `sign-in` next step, not a repair. A failed `harness` check adds an `install-agent` next step with the install command for the configured agent; `start` and `service` appear only when nothing blocks. If `worker doctor --help` lacks `--json`, run it without the flag and read the ❌, ⚠️, and 👉 rows with the same exit codes. Use `--offline` only when network checks are impossible, and say that query, repository, and license checks were skipped. If `devintern worker --help` does not list `doctor`, the installed CLI predates it: validate the TOML and relevant schema by hand instead, and do not invent a `worker validate` command.

`devintern doctor` checks readiness in its loaded project/environment context, not every repo/team in a workspace; inspect its output before claiming it tested remote credentials or worker authentication. Use `devintern worker connect status --workspace /path/to/workspace.toml` for relay pairing status, not as a complete worker health check.

Before starting a worker, inspect whether a service or daemon already owns the selected workspace (`devintern worker service status --json` and `devintern worker status --json`). Startup begins acquiring eligible work. Start the worker or install/start its user service when the user's requested setup includes activation; do not launch a second daemon. To run it in the background, use `devintern worker service install --json` (systemd user unit on Linux, launchd agent on macOS; no TTY needed). It runs the `worker doctor` checks first and refuses when the worker could not start: exit 2 / `result` `action_required` means only the sign-in is left (do that, then install again), exit 1 / `refused` lists the failing checks in `checks` (same shape as above) and one runnable `command` per `nextSteps` entry, with the explanation in `message`. After starting it waits for the worker itself and reports `result` `running` (exit 0), `failed` (exit 1; `start.reason` and `start.logLines` say why, `start.permanent` means the service stopped retrying until the problem is fixed and `devintern worker service restart` runs), or `starting` (exit 3; check again with `service status`). Report a failed or starting result as not running. Use `--force` only when the user accepts installing a worker that will not start yet. Relay `warnings` to the user, notably a lingering warning with its `sudo loginctl enable-linger <user>` command (without it the worker stops at logout). Other actions: `start`, `stop` (clean graceful stop), `restart`, `uninstall`, and `logs`. If `devintern worker --help` does not list `service`, the installed CLI predates it: follow the wizard's generated service instructions or the [service guide](https://devintern.com/docs/code/worker#running-as-a-service), including Bun/agent PATH and unattended git authentication. Changes to shared tracker credentials, tracker/team identity, or dashboard/startup settings require a restart (`devintern worker service restart` for a service); ordinary repo/query/routing edits can reload. Verify logs show that the requested configuration was accepted.

To check a running worker without the dashboard, use the read-only commands: `devintern worker status --json` (liveness, queue counts, poll cursors), `devintern worker overview --json` (capacity, harness chain health, tracker freshness), and `devintern worker logs --level warn` (recent reload messages, warnings, and errors). Pass `--workspace` for a nondefault workspace. If `devintern worker --help` does not list them, the installed CLI predates them; read the worker's log files or the dashboard instead.

Only run a trial task when covered by the user's request: it can modify files, transition tracker tickets, post comments, and create PRs. A passing `worker doctor`, configuration validation, and successful authorization are not proof that an implementation ran successfully.

Report the selected host/config, repositories and task sources, and evidence separately for: **configured**, **credentials verified**, **relay connected or polling-only**, and **worker running or intentionally stopped**, citing the `worker doctor` result. Identify remaining browser/user actions and any checks that could not be performed. Never include tokens, session data, or private ingest URLs.
